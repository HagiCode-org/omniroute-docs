# 术语表、官方提示词与全站翻译耗时复测

**当前改进方案约处理 1,250 个英文词/分钟、生成 2,400 个汉字/分钟；164 篇文档的纯生成估算约 3 小时，机翻与自动检查建议预留 4–6 小时。语义质量仍不足以无人校审直接发布。**

模型为本地 `hy-mt2:1.8b`（Q8_0）。[统计与逐项评价](./ollama-en-zh-cn-improved-2026-10-25.json)及[42 次最终对比的完整记录](./ollama-improved-2026-10-26T06-07-46-816Z.jsonl)保留源文、实际提示词、模型响应、恢复结果及耗时。运行时间为 2026-10-25 23:07–23:11（America/Los_Angeles）。

## 已实施的改进

- 新增[41 条术语及语境规则](./terminology.en-zh-CN.json)，区分 API 密钥、认证令牌与计量词元。仅提供当前正文出现的术语，避免无条件的 `token=词元` 干扰其他概念。
- 按用户提供的官方模板构造“参考下面的翻译”和默认翻译指令；改进方案再加入背景信息与分隔符约束。没有 system 消息，没有改用通用聊天助手角色提示词。
- 加入代码、链接、HTML、变量及 frontmatter 的提取与恢复。行内代码允许随中文语序换位；独立代码块与 HTML 标签顺序锁定。标记丢失或重复时拒绝恢复。
- 新增无需额外配置或参数的复测脚本及 7 项专项测试；用原有 12 组开发样本加 2 篇新增整文做最终三方案对比。

采样设置：`temperature=0.7`、`top_p=0.6`、`top_k=20`、`repeat_penalty=1.05`。输出上限为 `num_predict=4096`，对应用户给出的 1.8B 推荐 `max_tokens=4096`；另设 `num_ctx=8192` 和 `seed=42`。固定种子不保证相同输出。

英文模板也已实现并有单元测试；本轮模型实测使用中文模板。使用说明见[本地翻译试验入口](./README.md)。

## 每分钟能处理多少内容

以下为同一轮 14 组样本的聚合结果，各方案各执行一次。英文词数仅统计待译正文，剔除代码、URL 和 HTML 属性；汉字数不含标点、拉丁字符及代码。耗时包含模型调用，不含人工校审。

| 方案 | 英文词/分钟 | 汉字/分钟 | 生成 tokens/秒 | 格式检查通过 |
| --- | ---: | ---: | ---: | ---: |
| 官方默认模板 | 1,026 | 2,113 | 48.85 | 10/14 |
| 官方术语模板 | 1,090 | 2,066 | 48.95 | 10/14 |
| 术语＋背景＋程序保护 | 1,253 | 2,421 | 49.08 | 13/14 |

三种方案每种均处理 1,434 个英文正文词。改进方案总调用耗时 68.643 秒。程序保护减少了模型重新输出代码的工作量；模型本身的生成 token 速度没有明显变化。

首次评估约为 81 tokens/秒、1,600–1,800 英文词/分钟；本轮约为 49 tokens/秒。运行负载、上下文设置及样本组成不同，不能将速度差异全部归因于提示词。全站排期采用本轮较保守的实际速度。

上述吞吐量包含最终被拦截的样本：它也消耗了调用时间，其汉字数按原始响应统计。因此这是处理速度，不是“每分钟产出多少无需校对的成品”的指标。

## 整个 OmniRoute 文档需要多久

范围按当前站点实际导入的英文文章计算：`README.md` 加英文 `docs/`，不含 `docs/i18n/` 中的译文、应用 UI 字符串和其他仓库。统计使用 `createImportPlan({ locales: ["en-US"] })` 的结果，不写入生成目录。

- 固定上游版本：`a58000c7685f4091c7a6fd8ddf3ebce7d2ec67c3`。
- 共 **164 篇**，英文正文及标题约 **221,959 词**。
- 含代码及结构的 Markdown 约 3,211,201 字符，不能将这些字符全当成需要翻译的自然语言。
- 按每篇约 500 词一块粗算约 **527 块**；实际还需要依照段落、表格与代码边界分块。最大文章约 18,192 词，不能整篇直接发送。

纯生成线性估算：

```text
221,959 英文词 ÷ 1,253.44 词/分钟 = 177.08 分钟 ≈ 2 小时 57 分钟
```

**建议为单机顺序机翻、分块、自动校验及失败重试预留 4–6 小时。** 这是排期预留，并非全站已经跑完的实测。人工技术校审、术语修正及发布验证另计。

当前代码是抽样评估器，尚未实现或启动全站分块翻译。frontmatter 目前整体保留，正式全量处理时标题与描述需要单独的结构化翻译步骤。

## 正确率如何

不能将 `13/14` 的格式通过率解释为翻译正确率。执行助手逐项对照源文，按“未发现关键技术错误、可以作为待校对初稿”判定：

| 判断 | 数量 | 占比 |
| --- | ---: | ---: |
| 可作初稿，仍需润色和术语校对 | 8/14 | 57.1% |
| 有实质技术问题，需要修正 | 5/14 | 35.7% |
| 丢失保护标记，被程序拦截 | 1/14 | 7.1% |

这是有目的选取难点的小样本判定，**不是逐句准确率，也不能外推全站正确率为 57.1%**。没有独立人工金标准、重复试验或统计置信区间。

原有 12 组开发样本中，本轮仍有 7 组可作初稿，与上一轮数量相同。术语消歧和结构保护的局部改善已观察到，但未证明整体语义可用率提高。

实际改善包括：

- API 密钥用途正确，不再译为“词元”。
- 熔断器不再被解释为连接开关，`closed`、`open`、`half_open` 得以原样恢复。
- YAML 的代码与注释完整恢复，可复制配置中的 ASCII 引号保留。

仍然存在的主要问题：

| 样本 | 需要修正的内容 |
| --- | --- |
| `yaml_config` | 将环境变量指向独立配置文档的关系写反，且合并覆盖的优先关系不清。 |
| `strategy_table` | 将“在冷却窗口内排除提供商”写成“排除于冷却期之外”。 |
| `pinned_provider` | HTTP header 被译成“标题”。 |
| `fallback_errors` | 即使背景说明明确指出请求不进入冷却期，仍写成“后续请求也会进入冷却期”。 |
| `holdout_quota` | 将“unknown 不等于 exhausted”写成“容量并未耗尽”，把未知扩大成确定未耗尽。 |
| `memory_budget` | 遗漏 `inflight_bytes_budget` 对应的保护标记；返回 `output: null`，未当作成功译文。 |

可用初稿中也有待润色用语，例如 Combos 被译成“组合玩法”、key system 译成“键系统”，说明术语覆盖仍需继续积累。这个 1.8B 模型可以降低初稿成本，暂时不能承担无人校审的技术文档发布。

## 验证与限制

最终记录共 42 次响应，均正常结束而非触及输出上限。已校验源文 SHA-256、每个方案的样本数、恢复后的格式检查及聚合统计。

7 项新增专项测试及现有导入、导航、工作流相关测试合计 **16 项通过**。先前完整站点测试为 20/22，其中两项因已有 `dist/sitemap-index.xml` 缺失失败；尚未获得新的完整构建验证结果，因此不宣称全量测试通过。

保护器针对当前 Markdown 样本实现，不是完整 Markdown/MDX 解析器。语义主体、否定、状态含义、范围上下界和领域术语仍需人工对照；格式检查不能覆盖这些问题。
