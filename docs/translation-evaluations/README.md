# 本地 Ollama 翻译试验

完整操作步骤见[使用本地 Ollama 翻译 OmniRoute 文档](../ollama-translation-guide.md)，包含单篇翻译示例、术语维护、失败处理和全量处理边界。

当前评估英文到简体中文，使用本机已有的 `hy-mt2:1.8b`。不需要新增依赖、技能配置或命令行参数。在仓库根目录运行：

```sh
node scripts/evaluate-ollama-translation.mjs
```

脚本顺序执行三种方案：用户提供的官方中文默认模板、官方术语模板、术语加背景信息与代码保护。使用原有 12 个开发样本及 2 篇新增整文验证样本；记录保存在本目录带时间戳的 `ollama-improved-*.jsonl` 中，每次响应后写入，便于在中断后复核已完成部分。输出只进入评估记录，不写入站点文章或翻译审核基线。

## 术语与提示词

[术语表](./terminology.en-zh-CN.json)区分 `API key`、访问令牌、输入/输出词元；不设置无条件的 `token` 映射。独立的 `key` 仅在正文存在认证语境时提供“密钥”参考，配置中的 `per-key` 不匹配此映射。语境判断是启发式规则，混合多种语境的段落仍需要校审。

`source` 和 `aliases` 匹配实际正文，`target` 是参考译法。仅提供当前正文涉及的术语，代码、链接目标、HTML 属性不参与匹配。可选 `contextAny` 限定使用语境；可选 `background` 解释容易误解的领域概念，例如提供商冷却、熔断状态和准入拒绝。背景信息不能作为译文新增事实。

提示词采用用户提供的官方格式：

```text
参考下面的翻译：
API key 翻译成 API 密钥
provider 翻译成 提供商

将以下文本翻译为 简体中文，注意只需要输出翻译后的结果，不要额外解释：

{source_text}
```

改进方案在此基础上使用官方“背景信息”和“分隔符”思路：只加入匹配术语的领域背景，并要求逐字保留保护标记。没有 system 消息。中文和英文模板构造均有单元测试，实测对比使用中文模板。

1.8B 推理参数保持 `temperature=0.7`、`top_p=0.6`、`top_k=20`、`repeat_penalty=1.05`。用户提供的 `max_tokens=4096` 在 Ollama 中设置为 `num_predict=4096`。另设 `num_ctx=8192`，为输入、术语和输出留出空间；这与输出上限是两个不同参数。`seed=42` 用于减少随机干扰，不保证跨调用逐字一致。

## 保护与校验

`scripts/ollama-translation.mjs` 将代码块（含注释）、行内代码、链接目标、HTML 标签及属性、常见变量占位符和 frontmatter 替换为唯一标记，翻译后恢复原值。

标记丢失、重复或出现未知标记时拒绝恢复。行内标记允许随中文语序换位；代码块、HTML 标签及元数据标记保持原顺序。恢复后再比较代码、链接、标题层级、表格形状和元数据。`accepted_structure` 只表示通过这些格式检查，不表示语义正确；调用者不能将其当成发布批准。

这是针对当前文档样本的 Markdown 保护器，不是完整 CommonMark/MDX 解析器。尚未覆盖所有嵌套列表、缩进代码块、脚注、引用式链接简写或复杂模板语法；并未对全文渲染做验证。frontmatter 整体保留，所以正式翻译站点标题和描述时需要另设受结构约束的翻译步骤。

不要将整篇超长文档直接发送给模型。全量翻译还需要按段分块、恢复结构、处理失败与检查遗漏；当前脚本负责抽样评估和全站工作量统计，没有启动全站翻译。

## 验证

```sh
node --test test/ollama-translation.test.mjs
```

测试覆盖可复制代码、嵌套链接目标、HTML 属性、变量、标记损坏、合理语序换位、语境选择、官方提示词、截断响应和 HTTP 错误。语义质量由评估报告逐项说明，不用格式通过率替代翻译正确率。
