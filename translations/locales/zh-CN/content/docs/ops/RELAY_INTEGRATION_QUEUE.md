# 中继集成队列

`.mergify.yml` 中可选启用的 `relay-integration` 规则，用于处理一个预先组合、已由所有者审核的 PR。它不会启用 Mergify 批处理，不会更改订阅，不会替换贡献者的 PR，也不会豁免其验收要求。普通 PR 仍通过 `release` 的 squash 队列处理。

## 路由与准入

集成规则要求满足以下全部条件：

| 条件             | 所需值                                     |
| ---------------- | ------------------------------------------ |
| 目标分支         | `release/v3.8.52`                          |
| 源分支           | `fix/relay-integration-candidate-20261015` |
| PR 作者          | `diegosouzapw`                             |
| 所有者审批标签   | 同时包含 `queue` 与 `integration-reviewed` |
| PR 状态          | 非草稿且无冲突                             |
| 合并/更新方式    | `merge`，保留原始提交                      |

普通队列会排除集成标签以及保留的候选分支前缀。缺少标签或目标分支被更改时，候选 PR 必须保持未入队状态，而不能静默地以 squash 方式合并贡献者历史。集成规则保留普通合并的全部条件，并额外要求 `Gate / CI` 与 `Gate / Quality` 均返回明确通过的结果。其超时时间仍为 240 分钟。该配置未设置新的失败容忍额度、付费批处理设置、绕过身份、变基（rebase）或快进推送。

该约定由 `tests/unit/mergify-queue-config.test.ts` 进行测试。这项本地测试只检查配置语义，并不能证明服务已启用该规则，也不能证明集成候选版本通过了 CI。

## 启用是单独的前提条件

Mergify 从仓库的默认分支读取配置。配置 PR 本身即使包含该规则，也无法仅凭这一点激活它自己的新队列。请先确认：配置变更已通过现有策略准入，已存在于默认分支上，并且已被服务接受。在完成此次回读之前，不要为集成候选版本添加标签。如果现有的基础分支失败阻碍了首次落地，请报告 bootstrap HOLD；不要绕过检查、直接推送到 release、更改仓库设置或购买套餐。

该规则使用单个预先组合的 PR 与普通合并提交，而不是付费的批处理功能。在使用前，仍须验证服务端的配置接受情况与账户可用性；本地 YAML 测试无法证明其中任何一项。

## 准备候选版本

1. 获得对所选 PR 组以及每个受保护的指令差异块（hunk）的确切批准。检查 release 冻结状态，并与所有活动会话协调所有权。不要移动、合并或排队另一个会话的进行中分支。
2. 在自有的 worktree 中，记录实时的基础分支、按顺序排列的原始 PR 头部 SHA 以及贡献者。使用合并提交（而非副本、squash 或变基）集成这些确切的提交。必需的修复应保留在其原始的、已获授权的 PR 分支上；这些分支变化后，需刷新候选版本。
3. 核实每个所选头部都是候选版本的祖先。审阅完整的最终差异、译文、生成的制品以及 changelog 署名。保留原始 PR；复制其工作后也绝不能关闭它们。
4. 记录候选版本的 SHA/tree、lockfile、工具链与检查回执。完整验收要求在当前实际候选版本上执行干净的依赖安装，并通过所有适用的强制检查通道（lane）。聚焦检查、快速检查、借用依赖的检查以及草稿回执均不算验收。入队前须先解决所有失败。
5. 在添加两个审批标签之前，立即重新核对基础分支、原始头部、候选版本、所有权与策略。任何标识发生变化，都必须返回验证。若某个原始头部在排队期间发生移动，应停止准入，并重新构建、审阅该组；不要声称后来的头部已经过测试。

[MERGE_TRAIN.md](MERGE_TRAIN.md) 中描述的手动 train 流程可能有助于构建诊断用候选版本。其历史上“一次验证、多次合并”的捷径既不能准入此组，也不能准入不同的中间 squash 树。此队列仅用于经过审核的合并式整体落地；它并不构成允许落地红色中间版本的许可。

## 回读

服务端强制合并完成后，请核实实际落地的树、每个原始头部的祖先关系、原始 PR 的合并状态以及贡献者署名。头部已变更的 PR 可以保持打开状态；不要为了让该组看起来完整而手动关闭它。请验证生成的基础分支并报告任何分歧。部署与 release 发布需要单独的授权。

GitHub 可能在某个 PR 的提交变为可从基础分支到达后，将其间接标记为已合并，即使该 PR 自身的保护检查并未通过。因此，“已合并”标记不能替代完整候选版本的验证回执。

参考资料：[Mergify 配置来源](https://docs.mergify.com/configuration/file-format/)、[合并策略](https://docs.mergify.com/merge-queue/merge-strategies/)、[GitHub 间接合并](https://docs.github.com/en/pull-requests/reference/pull-request-merges)。
