# Каталог моделей CLI и ручные метаданные

`omniroute models` сначала читает публичный каталог моделей выбранного сервера, включая
его пользовательские и синхронизированные записи. `--output json` и `--output jsonl`
возвращают все подходящие строки, без сообщения об усечении таблицы. Интерактивные таблицы
показывают не более 50 строк. JSON сохраняет публичные лимиты контекста, модальности,
возможности, источник модели (если его передаёт сервер) и метаданные формата API; учётные данные и
заголовки совместимости не выводятся. Устаревший fallback `/api/models` используется только в том случае, если
публичный endpoint возвращает HTTP 404, 405 или 501, и никогда после сбоя аутентификации.
`omniroute completion refresh` использует тот же каталог. Неудачный запрос каталога моделей
возвращает ненулевой код выхода и сохраняет прежний кэш автодополнения. Скрипты автодополнения для Bash, Zsh
и Fish предлагают подкоманды ручного управления моделями.

## Жизненный цикл ручной модели

Эти операции используют существующий API управления `/api/provider-models` с аутентификацией.
Они учитывают тот же глобальный выбор `--context` и `--base-url`, что и другие команды
CLI. Указывайте канонический ID провайдера и ID модели провайдера отдельно; ID модели,
содержащий косые черты, допустим. Используйте настроенный контекст управления, а не
передавайте учётные данные в аргументах команды.

```bash
omniroute models openai --output json
omniroute models manual openai
omniroute models add openai my-model --name "My model" --context-window 32768 --dry-run
omniroute models add openai my-model --name "My model" --context-window 32768
omniroute models edit openai my-model --context-window 65536
omniroute models edit openai my-model --clear-context-window
omniroute models remove openai my-model --dry-run
omniroute models remove openai my-model --yes
```

Примеры описывают синтаксис; замените ID провайдера и модели на записи, относящиеся к вашему
серверу. Операция добавления не создаёт подключение к провайдеру.

- `add` отклоняет уже существующую пользовательскую запись. Необязательный `--max-output-tokens` задаёт
  лимит вывода при создании; `--api-format` задаёт формат API модели и соответствующие
  метаданные endpoint, например `embeddings`, а не `chat`.
- `edit` требует существующей ручной записи. Её лимит контекста использует независимое
  ручное переопределение контекста на стороне бэкенда; его очистка снимает это переопределение, а не
  исходный входной лимит или синхронизированные метаданные.
- `remove` требует `--yes`, за исключением режима `--dry-run`. Он запрашивает `resetOverride=true`,
  сохраняя синхронизированную запись с тем же ID. Массовое удаление не предоставляется.
- `--dry-run` выполняет предварительное чтение с аутентификацией, но не запись и не инференс.
- Каждое фактическое изменение считывает ручной каталог обратно. `persistenceVerified: true`
  означает, что запрошенные метаданные были обнаружены после записи; это не означает, что
  модель может генерировать текст или вызывать инструменты. `inferenceValidation` всегда равно `not-run`.
- Сбой readback возвращает ненулевой код выхода. Запись могла уже вступить в силу;
  проверьте сервер, прежде чем повторять попытку. Параллельные записи не сериализуются
  этим CLI, а существующий API не предоставляет транзакцию compare-and-swap.

## Test & Add: не реализовано

Ручные записи не проверены. Флага `--validate` нет, и эти команды
не отправляют запросы инференса и не выполняют инструменты. Будущий opt-in процесс проверки должен
разделять учётные данные инференса и аутентификацию управления и устанавливать, какое
именно подключение к провайдеру дало все три подтверждения: генерацию, синтетический вызов
инструмента, привязанный к nonce, и продолжение после синтетического результата инструмента. Реальное выполнение
инструментов для этих подтверждений не требуется.

Одного существующего закрепления `x-omniroute-connection` недостаточно в качестве receipt-подтверждения:
выбор учётных данных может намеренно снимать закрепление в случаях cooldown, квоты или
исключённой учётной записи, а в выборе участвует привязка сессии. См.
`src/sse/services/auth.ts` и обработку `forcedConnectionId` в
`src/sse/handlers/chat.ts`. Прежде чем реализовывать Test & Add, нужно определить контракт строгого закрепления или
проверяемого receipt подключения. Затем тесты должны доказать, что после любого
неудачного, усечённого, завершившегося по тайм-ауту ответа или ответа от неверного подключения ничего не сохраняется.
Это отдельное решение о контракте бэкенда, а не обещание, данное ручным CRUD.
