# Состояние аутентификации инференса

## Обзор

`GET /v1/models` и endpoint инференса защищаются **разными
настройками**. Поэтому самая естественная проверка, которую оператор выполняет, чтобы ответить на вопрос «защищён ли мой API?»,
может дать неверный ответ.

| Endpoint                                                                           | Чем защищён                                                                                                                                        |
| ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /v1/models`                                                                   | Режим входа в dashboard — `isAuthRequired()`, переопределяется для каждого экземпляра через `requireAuthForModels` (`src/app/api/v1/models/catalogRequest.ts`) |
| `POST /v1/chat/completions`, `POST /v1/responses` и другие маршруты клиентского API | `REQUIRE_API_KEY` (`src/server/authz/policies/clientApi.ts`)                                                                                       |

В экземпляре, где задан пароль администратора и `REQUIRE_API_KEY=false`,
`/v1/models` отвечает `401`, тогда как инференс открыт для любого, кто может достучаться до
порта.

> **Предупреждение о проверке:** ответ `401` от `/v1/models` **не** подтверждает, что
> инференс защищён. Он говорит лишь о том, что dashboard требует входа.

Это не гипотетическая ситуация. В обсуждении #13310 квота Codex экземпляра self-hosted за
Traefik расходовалась анонимным трафиком `POST /v1/responses`,
пока `/v1/models` возвращал `401` — что, по словам автора обращения, «изначально
создало впечатление, что весь API защищён» и заставило его искать причину не в том компоненте.

## Как проверить на самом деле

Проверяйте маршрут инференса, а не каталог:

```bash
curl -s -o /dev/null -w '%{http_code}\n' \
  -X POST http://<host>:<api-port>/v1/chat/completions \
  -H 'content-type: application/json' \
  -d '{"model":"<any-model>","messages":[{"role":"user","content":"ping"}]}'
```

Ответ `401` означает, что `REQUIRE_API_KEY` действует. Всё, что доходит до маршрутизации
(включая ошибку «модель не найдена»), означает, что анонимный трафик принимается.

Обратите внимание: при `REQUIRE_API_KEY=false` **недействительный** bearer понижается до
анонимного, а не отклоняется (#2257), поэтому отправка произвольного ключа тоже не является корректной
проверкой.

## Предупреждение при запуске

Если `REQUIRE_API_KEY` отключён, а сервер привязан к интерфейсу, отличному от loopback,
OmniRoute записывает предупреждение при загрузке (`src/lib/startup/nonLoopbackApiKeyGuard.ts`).
Оно охватывает три поверхности:

- сервер Dashboard/API, обслуживающий инференс `/v1` — `HOST`, по умолчанию `0.0.0.0`
- мост API — `API_HOST`, по умолчанию `127.0.0.1`
- WebSocket живого dashboard — собственный хост

Предупреждение никогда не блокирует загрузку: reverse proxy перед OmniRoute может
уже применять собственную аутентификацию.
